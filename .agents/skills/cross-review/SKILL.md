# Cross Review

依頼元のOrcaタブ内にレビュー用の2ペインを追加し、司令塔は元の会話に残る。最終回答はLGTM判定から始め、指摘を数字だけの固定ID・ジャンル・重要度・発生頻度で示す。

同梱資料への相対リンクは、このスキルのディレクトリを基準に解決する。

## 実行の境界

- 起動モデルはCodex `gpt-6.2-astra` / `ultra`、Claude Code `claude-opus-5-5` / `max`。一次レビューから相互検証まで同じ2セッションを使う。モデルを自動で代替しない。
- 両者を実装セッションから独立した新規セッションで起動する。両者とも対象全体をレビューし、分野で分担しない。
- ソース・index・branch・設定・スキルは読み取り専用。修正、commit、Push、GitHubへの投稿、追加worker、git worktreeの作成はレビューに含めない。修正依頼は別タスクとして扱う。
- 対象リポジトリの操作・権限に関する制約を委任先にも渡す。GitHubへのレビューコメントは案だけ返す。
- 通常の単独レビュー用スキルは丸ごと起動しない。独自のworker起動・自動修正と競合するため、必要な専門観点だけ参照する。
- Orcaを使えない、依頼元を特定できない、指定モデル・強度を確認できない場合は、できた範囲と不足を示して `LGTM: 保留`。別タブや非Orca subagentに黙って切り替えない。

## 1. 同じ対象と仕様を共有する

対象リポジトリに適用されるAGENTS.md / CLAUDE.mdを読む。複数のリポジトリがある場合は対象ごとにGit操作を行う。ユーザーの指定がなければ依頼元のworkspaceと作業差分から候補を確認し、対象を明示する。

| 依頼 | 対象 |
|---|---|
| 他人のPR | PR本文・承認仕様と、固定したbase SHA / head SHAから求めたmerge-base→headの差分。既存コメント・CIも確認 |
| 自分の開発・Push前 | 予定しているマージ先とのmerge-base→現在のHEAD、およびstaged / unstaged / 対象の未追跡ファイル |
| 指定範囲 | 指定コミット・差分。未コミット変更を含むか明示 |

- `HEAD~1` や未Pushコミットだけへ勝手に狭めない。対象が本当に決められないときだけ一問確認する。秘密情報や無関係な未追跡ファイルは含めない。
- PRのheadが現在のcheckoutと異なる場合、checkoutせず固定SHAの `git show` / `git grep` 等で周辺コードも読む。別ブランチの作業ファイルをPRの実装と取り違えない。そのcheckoutでPRのテストを実行しない。
- 実装者の結論や疑っているバグを初期プロンプトへ入れず、両者に同じ仕様・差分・制約・関連資料を渡す。
- レビュー記録は司令塔と両者が参照できる作業用ディレクトリに置く。ユーザー指定がなければリポジトリ外の一時ディレクトリを使う。対象repo / base・head・merge-base SHA / 差分範囲 / 仕様 / 対象未追跡ファイルを `target.md` に記録する。
- [レビュー対象の固定手順](references/target.md) に沿って、開始・各フェーズ終了・最終報告前に対象の版と仕様を照合する。無関係な変更だけでは失効させない。照合できなければ保留にする。
- これは変更検知であり、コードを凍結する仕組みではない。途中で対象・読んだ関連コード・仕様が変われば結果を失効させ、変更箇所を含め両者が再確認するまで可にしない。古い結果・番号・未解決事項は消さない。

## 2. 依頼元タブに2ペインを開く

[references/orca-panes.md](references/orca-panes.md) を読み、バージョンに合った `orca-cli` / `orchestration` のガイドを取得して実行する。

- 元のペインを残し、その右にCodex、右側の下にClaudeを開く。既存レイアウトは元ペインの領域だけ分割し、他のペインを動かさない。
- 対象・originのworkspace / tab / pane / handle・reviewerのhandle / session / Task / Dispatch / 実行設定と確認証拠を `session.json` に残す。固定UUIDや画面のactive状態に依存しない。
- 同じ実行の続きでは記録と実セッションを照合して再利用する。新しい対象のレビューは新規セッションにする。前回のペインを無断で閉じたり再利用したりしない。
- レビュー完了後も2ペインを保持する。

## 3. 独立レビューを2本実行する

両者へ [references/reviewer-contract.md](references/reviewer-contract.md) とtargetの絶対パスを渡し、初回は `phase=independent` とする。専門用語やスキル名だけで委任せず、対象・読み取り範囲・制約・完了条件をTaskに含める。

- 両者の一次結果が届くまでは相手の指摘・結果ファイル・会話を共有しない。
- 呼び出し元・関連処理・API契約・既存テストまで確認させる。テスト方針は対象リポジトリに従う。RSpecを評価する場合は利用可能なら `rspec-quality` の観点を参照する。
- 検証コマンドは司令塔が調整する。DBなど同じ状態を使うテストを両者で同時実行しない。環境・権限・データの変更が必要なら実行せず不足を報告する。ブラウザ操作が必要なら権限と対象版を司令塔が確認し、利用可能なら `orca-qa` を別途実行する。
- プロセス終了や無応答を完了とみなさず、両者の結果・対象一致・制限を確認する。

## 4. 番号を固定して相互検証する

両者の一次指摘を司令塔が `findings.md` にまとめる。同じ原因・発生条件・症状の指摘だけ統合する。

- ユーザー向けIDは **1、2、3…だけ**。両repo・全ジャンル・未合意事項を通じた連番で、一度表示した番号は変更・再利用しない。並び替え・取り下げ後も欠番を許容する。
- 一次レビューではworkerに独自の番号を付けさせず、見出し・場所・原因で照合する。数字IDは司令塔だけが発行し、両ペインに対応表を共有する。後から重複と分かった場合は元の番号から統合先を追えるよう残す。
- Codexの指摘はClaudeへ、Claudeの指摘はCodexへ渡す。重複指摘も相互検証を省略しない。自分の指摘への反証も受け取り、現時点の判定を返させる。
- 判定は **同意 / 反対 / 判断不能**。実コード・仕様・再現結果による根拠を求める。「相手も言っている」「納得した」だけを同意の証拠にしない。
- **同じ版の指摘の、問題の存在・発生条件・影響・重要度・頻度分類に両者が明示的に同意**した場合だけ確定する。文章や修正方法の完全一致は不要。片方が指摘を改訂したら、改訂後の内容へのもう片方の同意を取り直す。
- 自動処理は相互検証1回＋食い違いの再確認1回まで。後から出た新規指摘も両者が検証できなければ未合意に残す。合意を目的に譲歩させたり、司令塔が片方の判断を採用して合意と呼んだりしない。
- 上限後も割れた指摘、重大な仕様質問、未検証事項は消さず「未合意・要確認」へ。両者が根拠付きで棄却した候補は取り下げ理由を記録し、最終一覧は省略してよい。

## 5. ユーザーの短いツッコミを受け付ける

追加質問は番号だけで対象を引けるようにする。

| 入力例 | 処理 |
|---|---|
| `2詳しく` | 2の発生条件・実コード・ユーザーへの影響を説明 |
| `2は仕様` | 仕様の追加情報として両者へ渡して再判定 |
| `3再確認` / `3なしでは？` | 異論として両者へ渡す。自動で取り下げない |
| `1はMUSTで` | 分類への意見として両者に根拠と分類を再確認させる |
| `1 OK` | 指摘への了解として記録。修正・Push・投稿の許可にはしない |

ユーザーからの明示的な再確認は自動ラウンド上限後も行える。最新の仕様・対象・指摘の版を両者へ共有し、片方だけの回答で合意やLGTM判定を更新しない。実装が変わった場合は変更検知もやり直す。

## 6. LGTMから始めて報告する

分類・判定・出力例は [references/report.md](references/report.md) に従う。

- 最初の行を `LGTM: 可 / 保留 / 不可` にする。続けて修正必須・推奨・要確認の件数と理由を短く書く。
- 合意済み指摘をジャンル別に表示し、各ジャンル内は重要度順、同じ重要度では毎回→条件付き→レアケース→該当なしの順。番号は振り直さない。
- 次に「未合意・要確認」、番号ごとの根拠・位置・影響、未検証範囲、対象と検証結果を示す。指摘のないジャンルは省略する。
- 他人のPRには合意済み指摘の投稿用コメント案も付け、投稿先の最新headのファイル・行番号を添える。未合意事項を確定的な指摘コメントにしない。投稿はしない。
- 合意済み0件は問題なしの証明ではない。両モデル・対象・必要な検証が完了した範囲で判断する。
