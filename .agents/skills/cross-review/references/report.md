# 分類と最終回答

## 判定を最初に示す

| 判定 | 条件 |
|---|---|
| LGTM: 不可 | 合意済みMUST、または対象変更に関係する既知の必須チェック失敗が残る |
| LGTM: 保留 | 重大になり得る未合意指摘・仕様質問、重要な未検証範囲、片方の実行失敗、指定モデル/強度の確認不足、対象の変更がある |
| LGTM: 可 | 両者の全対象レビュー・相互検証と必要な確認が完了し、MUSTも重大な未確定事項もない |

既知のMUSTがあれば未検証事項も併記して不可とする。無関係と確認できたCI失敗だけでは不可にしない。SHOULD / IMO / NITSや軽微な未合意提案だけでは可を妨げないが、非ブロッキングと判断した理由を示す。

LGTMはレビュー対象に対する判断であり、Push・マージ・公開・修正の実行許可ではない。

## ジャンル

1指摘に主なジャンルを1つ割り当て、重複掲載しない。順番は次を標準とする。対象によってセキュリティ等の重大なジャンルを先に出してよい。

- 動作・仕様
- セキュリティ
- パフォーマンス
- 可読性・設計
- UI・UX
- テスト・リリース

## 重要度

| 重要度 | 判断 |
|---|---|
| MUST | マージ/Push前に直す必要のあるバグ、金銭・データ・権限・主要操作の問題、または重大な回帰防止に不可欠な検証不足 |
| SHOULD | ユーザー体験・性能・運用・保守性のため今回の修正を強く勧めるが、単独では止めない |
| IMO | 不具合と断定できない設計・命名・書き方の改善提案 |
| NITS | 挙動に影響しない軽微な表記・スタイル・コメント |

`ASK` は重要度に混ぜず「要確認」として扱う。可読性・きれいな書き方は、既存方針と具体的な誤読・修正漏れのリスクで説明する。単なる個人の好みや、不要なリファクタの要求をMUSTにしない。

## 発生頻度

| 分類 | 判断 |
|---|---|
| 毎回 | 対象機能の通常操作で必ず起きる |
| 条件付き | 特定のユーザー状態・設定・データ・環境で起きる。条件を具体的に書く |
| レアケース | 特殊な操作順や限られたタイミングで起きる。意図的に再現できるかも書く |
| 該当なし | 実行時の症状を持たない可読性・設計・表記などの提案 |

実測の発生率ではなく発生条件の分類。ログや利用実態がなければ割合を捏造しない。同時実行だからレアとは限らず、頻度不明なら条件付きとして条件と不明点を書く。レアでも二重課金や権限漏れならMUSTになり得る。重要度と頻度を掛け合わせた点数で自動降格させない。

## 最終出力例（架空）

```text
LGTM: 不可
修正必須 1件 / 推奨 1件 / 要確認 1件
理由: 購入履歴の権限チェック漏れが残っているため。

合意済みの指摘

セキュリティ
  1 [MUST][条件付き] 他人の購入履歴を取得できる

可読性・設計
  3 [SHOULD][該当なし] 同じ判定が3か所に分散している

未合意・要確認
  2 [動作・仕様][条件付き] 期限の境界で購入できなくなる
    Codex: 不具合 / Claude: 終了時刻の仕様確認が必要

詳細
  1. repo/path:line
     どの操作で何が起きるか。発生条件と根拠。
     ユーザーへの影響。売上・管理画面・集計・CS等の影響。
     両者の検証根拠と最小の修正方向。
  2. ...
  3. ...

対象・確認範囲
  repo、固定SHAまたは作業差分、実行モデルと強度、検証結果、未検証事項。
```

- 修正必須は合意済みMUST、推奨は合意済みSHOULD、要確認は未合意・質問の件数。IMO/NITSがあれば件数を短く添える。重複・取り下げ候補は数えない。
- 合意済み0件ならその旨と未検証範囲を書く。指摘なしのジャンルは出さない。
- 番号はジャンルをまたいで固定する。セクションを移動しても元の番号を使い、「2は仕様」の対象を変えない。
- file:lineは実際に確認した番号を使う。差分外の問題は最寄りの原因となる変更行と関連箇所を分ける。位置を推測しない。
- PR用コメント案は `[MUST][条件付き]` 等で始め、ユーザーの操作と症状、根拠、最小の対応方向を書く。各案に投稿先のfile:lineを添える。
