# Implement Todo

指定された Markdown のタスクを、ブランチ作成から実装、レビュー、コミット、チェック更新まで処理する。

## 入力

| 引数 | 必須 | 説明 |
|---|---|---|
| `file` | ○ | 対象のタスクファイル |
| `branch_type` | × | `feature` / `fix` / `refactor` / `chore` など。デフォルトは `feature` |

## 前提

- Git 操作はタスクで指定されたリポジトリ内で行う。
- 実装前に対象 repo の `CLAUDE.md` / `AGENTS.md` を読む。
- push しない。
- ユーザーが対象を確認して明示的に許可するまで、stageもcommitもしない。
- 既存の未コミット変更を記録する。今回分と安全に切り分けられない箇所は、編集前に確認する。

## 仕様判断が必要な場合の停止ルール

実装中、レビュー中、レビュー指摘の修正中を問わず、次のいずれかが発生した時点で作業を止める。

- タスクの仕様に問題があり、受け入れ条件、画面遷移、文言、業務ルール、API契約、データの扱い、運用を変更したい。
- 仕様にない判断が必要で、選択によってユーザー体験またはプロダクトの挙動が変わる。
- レビュー指摘が仕様不備に起因し、コードだけでは正解を確定できない。

停止時はコード変更、コミット、チェックボックス更新、次タスクへの着手を行わず、次の順でユーザーに説明する。

1. どの手順で、何が見つかったか。
2. 現在の仕様・実装のままだと、ユーザーに何が起きるか。
3. プロダクト・運用・KPI・CSにどんな影響があり得るか。
4. 選択肢と、それぞれのトレードオフ。
5. 推奨案と理由。
6. 判断に必要な質問を一問だけ行う。

回答を受けたら、必要に応じて次の質問を一問だけ行う。この手順を繰り返して判断を確定してから、停止した箇所から再開する。既存パターンから一意に決まる機械的な実装詳細で、ユーザー体験・仕様・API契約を変えないものは確認対象にしない。

## 実装手順

1. 指定されたタスクファイル を読み、次を抽出する。
   - ID
   - タイトル
   - 関連資料の URL（あれば）
   - 未完了タスク
   - 関連ファイル
   - 対象 repo
2. 対象 repo ごとに、指定された起点と命名規則に従ってブランチを切る。規約がなければマージ先を確認し、タスク名から短いブランチ名を付ける。
3. 未完了タスクを上から1件ずつ処理する。順番を変えない。
4. 各タスクで次を行う。
   - 内容と関連ファイルを確認する。
   - 既存パターンに合わせて実装する。
   - 必要な lint / test を実行する。
   - 下の「Subagentレビュー」を完了する。
   - レビュー完了後、下の「コミット許可」を行う。
   - ユーザーの明示許可後だけコミットする。
   - コミット成功後、タスク文書の対応するチェックを `- [x]` に更新する。
5. 「計測」「要確認」「要検討」など、実装ではなく調査や判断待ちのタスクはスキップし、理由を残す。

## Subagentレビュー

各タスクの未コミット差分に対して、レビューと修正を最大4ラウンド行う。1ラウンドは、同じ時点の差分を対象に必要なsubagentを起動し、main agentが結果を統合するまでとする。Backend / Admin / Web / Appなど複数面のsubagentを同時に使っても、同じ差分に対するものは1ラウンドと数える。

### ラウンドごとの手順

1. 新規のread-only subagentを起動し、差分と周辺コードをレビューさせる。
   - サーバー変更では DB、API、性能、権限、回帰テストを確認させる。
   - UI変更では操作導線、状態管理、権限表示、API互換性、運用影響を確認させる。クライアントとサーバーの配信が別ならリリース順も対象にする。
   - 複数repoの変更: repo別subagentに加え、main agentがAPI契約とリリース順を横断確認する。
2. subagentには編集させず、`指摘 / severity / 根拠 / file:line / ユーザー症状 / プロダクト影響 / 修正案 / 未確認事項` を返させる。
3. main agentが差分と周辺コードを確認し、誤検知・重複を除いてseverityを確定する。subagentの判断をそのまま採用しない。
4. 確定したHighがなければレビュー完了とし、Medium / Lowと未確認リスクを完了報告に残す。
5. Highがあり、仕様判断なしで修正が明確ならmain agentが修正し、関連lint / testを実行して次ラウンドへ進む。
6. Highの修正に仕様変更または未定義の判断が必要なら、「仕様判断が必要な場合の停止ルール」に従って即停止する。

可能な限り各ラウンドで新しいsubagentを使い、前ラウンドの結論を答えとして渡さない。修正後の差分と必要最小限のタスク仕様だけを渡し、独立して再確認させる。subagentを利用できない場合はレビュー完了扱いにせず、理由を報告して作業を止める。

### Highの基準

Highは、実装の完了前に解決が必要な次の問題とする。

- 主要機能が仕様どおり動かない、または重要な操作が完了できない。
- セキュリティ、権限、個人情報、データ破損・消失、二重処理、決済に重大なリスクがある。
- API契約やリリース順の不整合により、App / Web / Adminのいずれかが壊れる。
- 本番性能、マイグレーション、集計・運用に重大な事故リスクがある。
- publicな振る舞いに必要なテストがなく、重大な回帰を検知できない。

### 4ラウンド目

- Highがなければレビュー完了とする。
- Highが残り、修正が明確で仕様判断が不要なら修正とlint / testまでは行うが、5ラウンド目は開始しない。そこで作業を止め、最終修正がsubagent未レビューであることを報告する。コミットとチェック更新は行わない。
- Highの修正内容が明確でない、または仕様判断が必要なら修正せず、その場で作業を止める。「仕様判断が必要な場合の停止ルール」に従って説明と質問を行う。
- レビュー回数の上限をmain agentの自己レビューで迂回しない。

## コミットのルール

- 「実装して」「最後まで進めて」など、作業開始時の依頼をコミット許可とみなさない。
- 許可は、直前に提示した対象repo・タスク・コミット案にだけ適用する。提示していないコミットや、その後に変更した差分へ流用しない。
- 変更ファイルを個別に `git add` する。`git add .` / `git add -A` は使わない。
- 1タスク1コミットを基本にする。
- 複数repoに変更がある場合は、repoごとに対象とコミットを示す。
- Highなしでレビューを完了し、必須チェックが通り、ユーザーが明示許可したタスクだけコミットする。

## コミット許可

Highなしでレビューを完了したら、stageせずに作業を止め、次を提示する。

- 対象repo、タスク、変更ファイル。
- 実行したlint / testと結果。
- レビューラウンド数、Medium / Low、未確認リスク。
- 変更した画面・クライアント・運用経路と、レビュワーが重視する箇所。
- repoごとのコミットメッセージ案。

最後に「提示したコミット案をコミットしてよいか」を一問だけ聞く。明示許可を受けるまで、`git add`、`git commit`、Todoのチェック更新、次タスクへの着手を行わない。

- 許可された場合: 対象ファイルだけをstageしてコミットし、成功後にTodoを更新して次タスクへ進む。
- 修正を求められた場合: 修正後に必要なlint / testとSubagentレビューを行い、更新したコミット案について改めて許可を得る。
- 許可されなかった場合または回答待ちの場合: 状態を `コミット許可待ち` とし、未コミットのまま停止する。

## 完了・停止・許可待ち時の出力

全タスクを完了・スキップした時、4ラウンド目で停止した時、またはコミット許可を待つ時は、次を手短に報告する。

- 状態: `完了`、`レビュー上限で停止`、または `コミット許可待ち`。
- タスクファイル、完了数 / スキップ数、ブランチ名、コミット一覧。
- レビューラウンド数、残ったHigh / Medium / Low、未確認リスク。
- スキップ項目と理由、次に人が行うこと。
- 変更のある面ごとに、ユーザー・運用への影響と確認内容。

4ラウンド目で停止した場合は、未コミット・未チェックのタスク、最終修正が未レビューかどうか、解消に必要な判断または次の確認箇所を明記し、完了したとは表現しない。

## 注意

- 大きく逸れる設計変更に広げない。
- コミット前は、対象repoの規約で指定された関連テスト・lint・型チェックを実行する。
