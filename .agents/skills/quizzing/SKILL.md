# Quizzing

対象を先に調査し、ユーザーが設計と実装を自分の言葉で説明できるまで、一問ずつ自由回答で問う。

## 対象を決める

1. ユーザーが指定した path、PR、document、topic、plan、implementation、diff を対象にする。
2. 対象が省略された場合は、このセッションで直近に扱った計画、実装、または差分を使う。
3. 対象を一意に決められない場合だけ、何を対象にするか一問で確認する。
4. 対象がサーバー、クライアント、または両者をまたぐかを把握する。

## 出題前に調査する

- 対象 repo の `CLAUDE.md` / `AGENTS.md` と、対象コード・差分・資料を読む。
- 小さい対象は直接読む。大きい対象は責務や処理経路ごとに分けて調査する。
- subagent は、ユーザーが明示的に利用を許可し、現在の指示でも許可されている場合だけ使う。
- コードで確認できる事実をユーザーに質問しない。事実を踏まえ、その理由、つながり、変更影響を問う。
- 調査できていない事実を正解として断定しない。採点前に追加調査する。

## 一問ずつ出題する

- 一度に一問だけ、選択肢のない自由回答で聞く。
- ユーザーが答える前に正解、誘導、採点基準を明かさない。
- `why`、`how`、`what-if` を混ぜる。
  - 計画・設計では、目的、判断理由、却下した代替案を優先する。
  - コード・差分では、実際の挙動、データフロー、境界、失敗時、変更影響を優先する。
- 丸暗記ではなく、「入力 → 判断 → 状態変化 → 出力・画面 → 失敗時」の因果を説明させる。
- 弱い論点は前提を小さく分解して掘り下げ、理解できた論点は繰り返さず次へ進む。

## 対象に合う観点を選ぶ

対象に関係する観点だけを出題する。

### Backend

- controller、serializer、model、job、DB、外部サービスの責務とデータフロー
- transaction、validation、権限、冪等性、失敗時や再実行時の挙動
- APIの後方互換、クライアントのバージョンやプラットフォームによる差、テストで保証する公開の振る舞い

### App

- route、screen、component、hook、state、API client、型の責務とデータフロー
- loading、empty、error、再試行、画面遷移、iOS / Android / Web の差
- OTA更新やストア更新で反映する変更か、旧版との短期的な互換が必要か

### Backend / App / WebView 横断

- 認証情報やクライアント環境をAPIへ伝える経路
- WebとネイティブUIの責務、`postMessage`、戻る導線、成功・失敗時の境界
- APIデプロイ、OTA更新、ストア更新の順序が一時的不整合を生まないか

### ユーザー・プロダクト

- ユーザーのどの画面・操作・待ち時間・エラー表示が変わるか
- KPI、売上、継続率、問い合わせ、管理画面、運用負荷、障害リスクへどう影響するか
- 技術的に成功しても体験や運用が失敗するケースは何か

## 回答を採点する

回答後、次の順で短く返してから次の一問を出す。

1. `判定: OK / 惜しい / 要復習` のいずれかを示す。
2. 正しく説明できた点を確認する。
3. 誤りを具体的に訂正する。
4. 抜けている重要点を補う。
5. その理解を試す次の一問だけを出す。

曖昧な表現を雰囲気で正解にしない。ただし言葉遣いではなく、因果関係と実際の挙動を採点する。

## 終了する

主要な責務、データフロー、設計理由、失敗・変更影響、ユーザー体験、プロダクト影響を対象範囲内で説明できたら終了する。

最後に次だけをまとめる。

- 理解できていた点
- 残っている弱点
- 後で復習する具体的なファイル・論点

クイズ中は仕様決定、コード変更、レビュー指摘の作成へ移らない。ユーザーが別途依頼した場合は、クイズを終えた後の別タスクとして扱う。
