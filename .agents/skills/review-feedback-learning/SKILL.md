# Review Feedback Learning

PRレビューコメントから、今後も再利用できる人間レビューの観点だけを抽出し、適切な instruction surface に短く反映する。目的は「このPRの修正メモ」を残すことではなく、将来のレビュー漏れを減らすこと。

## Non-Negotiables

- main agent がこのskillを使う時は、利用が許可された subagent があれば、コメント収集・一次分類を任せる。対象が少ない場合や委任できない環境では、自分で同じ条件に沿って分類する。
- すでに親agentから委譲された subagent としてこのskillを読む場合は、追加の nested subagent を起動しない。自分が分類担当としてコメント収集・一次分類を行い、ファイル編集はしない。
- Devin、CLAUDE、GitHub Actions、Dependabot、Copilot などの自動レビューは除外する。
- 人間コメントでも、そのPR固有の文言、slug、画像名、QA事情、一回限りの実装都合は除外する。
- 妥当で、他の開発でも使える指摘だけ採用する。
- コメント本文をそのまま貼らない。短いチェック項目へ抽象化する。

## Workflow

1. 対象PRを決める。
   - ユーザーがPR URLや番号を指定していればそれを使う。
   - 「今回のPR」「今のPR」など曖昧な場合は、`gh pr list` / branch / remote から候補を探索する。
   - 複数候補があり判断できない時だけユーザーに確認する。

2. コメントの収集・一次分類を担当する方法を決める。
   - 委任が許可され、対象が多い場合は subagent に PR URL/番号、repo path、下記の抽出条件、出力形式を渡す。subagent の担当はコメント取得と分類まで。
   - 対象が少ない場合、委任できない場合、すでに自分が分類担当として委任されている場合は、自分で次の手順を実行する。

3. 担当者はコメントを収集し、同じ条件で一次分類する。
   - GitHub PR review comments、issue comments、review summary を取得する。
   - author が bot のものを除外する。
   - アカウント種別、Botの表示、スレッドの内容から自動レビューを除く。名前の部分一致だけで人間かどうかを判断しない。
   - PR author 自身の返信は、レビュー指摘ではなく会話補足として扱い、原則採用候補から外す。
   - 残った人間コメントを以下に分類する。
     - `adopt`: 今後も使える妥当なレビュー観点。
     - `skip_pr_specific`: そのPR固有で再利用しづらい。
     - `skip_already_covered`: 既存 AGENTS/skills に十分ある。
     - `unclear`: 採用判断に仕様・好みの確認が必要。
   - `adopt` は「元コメントの要旨」「抽象化したチェック項目」「推奨追記先」を返す。

4. main agent が最終判断する。
   - 採用候補は指摘の根拠を確認し、既存の指示と重複していないか調べる。
   - 採用数は最小限にする。1つのレビュー観点につき1行から数行で十分。
   - 判断に迷うものは採用しないか、ユーザーに確認する。

5. 追記先を選ぶ。
   - 特定の技術やレビュー手順に効く観点は、対象技術のレビュースキルへ。
   - すべての作業で常時守るべき方針: root `AGENTS.md`
   - 既存skillに入れると不自然で、独立して繰り返し使うワークフローなら、新規 skill を作る。

6. 反映まで依頼されていれば編集する。
   - 追記前に対象ファイルを読む。
   - 既存の近い見出しへ追記し、末尾に雑に増やさない。
   - 似た内容がある場合は、重複行を増やさず既存項目を少し広げる。
   - PR固有名詞を残す必要がある場合は、原則として採用しない。

7. 確認する。
   - 変更後に該当範囲を読み返す。
   - 新規 skill を作った場合は `skill-creator` の `quick_validate.py` が利用できれば実行する。利用できない場合は必須の frontmatter とリンクを確認する。
   - 最終報告には、採用した観点、除外した代表理由、変更ファイルを短く書く。

## Subagent Prompt Template

```text
PRレビューコメントから、今後の開発にも再利用できる人間レビュー指摘だけを抽出してください。ファイル編集はしないでください。

対象:
- repo: <repo path>
- PR: <PR URL or number>

条件:
- Devin、CLAUDE、GitHub Actions、Dependabot、Copilotなど自動レビューは除外してください。
- アカウント種別とスレッドから自動レビューを除外してください。
- PR author本人の返信は原則採用候補から外してください。
- PR固有のslug、画像、文言、QA事情、一回限りの実装都合は skip_pr_specific にしてください。
- 他の開発でも使える、妥当なレビュー観点だけ adopt にしてください。
- 対象リポジトリのAGENTS.mdや該当レビュースキル に既に十分あるものは skip_already_covered にしてください。

出力:
- adopt: 元コメント要旨 / 抽象化したチェック項目 / 推奨追記先
- skip_pr_specific: 元コメント要旨 / 理由
- skip_already_covered: 元コメント要旨 / 既存の該当箇所
- unclear: 元コメント要旨 / 何を確認すべきか
```

## Adoption Heuristics

採用しやすいもの:

- 複数クライアントで共有する業務ルールを、どの境界で一貫して適用するかを確認する。
- TOPやマイページなど高頻度画面で重いAPI・クエリを避ける。
- Rails SCSS のグローバル漏れを防ぐ。
- 既存ドメインでは許容されているデータを、新機能側で意図せず永続エラーにしない。
- scope / relation / serializer / API shape など、今後も同じミスが起こりやすい設計観点。

採用しないもの:

- 「今回の画像名が違う」「今回の識別子をチケットに書く」など、そのPRだけで閉じるもの。
- 好みの範囲で、プロダクト影響や保守性への説明が弱いもの。
- 既存skillにすでに同等のチェック項目があるもの。
- 自動レビュー由来のもの。ただし、人間レビュアーが同じ論点を明示的に支持・再指摘している場合は、人間コメントとして扱ってよい。
