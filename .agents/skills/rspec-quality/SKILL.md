# RSpec の品質

リポジトリの規約と既存 Spec から、実行環境、データセットアップ、テスト層の分担を確認する。利用側の契約を守れる粒度でケースを選ぶ。

## ケースを選ぶ

1. 仕様、呼び出し元、対象コード、関連Spec、既存のFactory・認証・時刻ヘルパーを読む。現在の実装から期待値を逆算せず、要求される振る舞いを確認する。
2. 変更に関わる「条件 → 操作 → 観察できる結果」を整理する。残高、在庫、権限、発送、通知など、失敗した場合にユーザーや運用に何が起きるかと結び付ける。
3. 正常系に加え、関連する境界・拒否・例外を選ぶ。閾値の直前・一致・直後、未認証・権限不足、失敗時の副作用などを確認する。複数条件が絡む場合は小さな決定表で漏れを探す。
4. 既存Specが保証している内容を確認し、必要な差分を補う。決済・ポイント・在庫など、不整合の影響が大きい振る舞いを優先する。

フレームワーク標準の単純な関連・検証や自動生成コードには、別のSpecで振る舞いを保証できていれば同じ検証を重ねない。独自の条件や複雑な検証は対象にする。
カバレッジ100%や組み合わせの総当たりを目標にせず、各ケースでどの不具合を検知するか説明できるようにする。

## Specを書く・読む基準

### 外から観察できる結果

- publicメソッド、HTTPリクエストなど、利用側の入口から検証する。privateを `send` 等で直接呼ばない。
- 戻り値、保存された状態、レスポンスの内容、通知などを確かめる。内部メソッドの呼び出しだけで業務上の成功を判断しない。
- request specではHTTPステータスに加え、今回の契約に関わるレスポンスやデータを確認する。service specなどで同じ業務ルールを保証済みなら、入口固有の認証・パラメータ・応答に集中する。
- 拒否・失敗ケースは、関連する残高や在庫が変わらず、不要な履歴や通知が増えないことも確認する。例外処理では、利用側に返る結果と保存状態の整合性を見る。

### 成功を取り違えない検証

- 更新はAからBへの変化、削除は存在していた対象の消失を確認する。処理後の値だけで、最初からその状態だった可能性を見逃さない。必要なデータを操作前に用意し、`let` の遅延生成が `change` の増減に紛れ込まないようにする。
- DBへの保存を保証する箇所は `reload` や再取得を使う。メモリ上の値だけで成功にしない。
- 期待する金額・件数などは、仕様から導いた具体値にする。例として、在庫100個から40個を確保するなら残数60個を期待する。実装と同じ計算式やテスト対象の戻り値を期待値に使わない。Factoryで生成したIDや固定した時刻を参照するのはよい。
- Arrange（準備）→ Act（対象の操作）→ Assert（結果の検証）の順が追えるようにする。同じ結果を検証するために副作用のある操作を繰り返さない。二重送信・再試行の検証では、必要な回数と順序を明示する。

### 仕様を読み取れる構成

- `context` と `it` で条件と期待結果が分かる名前を付ける。必要なデータと操作の関係を近くに置く。
- `let`・`subject`・`before`・`shared_examples` は、読みやすくなる場合に使う。遠い定義、深いネスト、暗黙の更新で準備や実行順が追いにくくなるなら、ケース内に明示する。
- `subject` の使用、1ケース1個の `expect`、ネストの段数などを一律に強制しない。1つの振る舞いに関する複数の検証を同じケースに置いてよい。
- 少量の重複は許容する。共通化する場合は、同じ契約を共有していることと、各ケースの条件・期待結果が読み取れることを確かめる。
- テスト内の条件分岐や複雑なループで期待結果を計算しない。異なる条件は明示したケースに分ける。単純なケース表の使用まで禁止しない。
- 現実の利用場面を想像できる名前・状態・金額のデータを、検証に必要な量だけ用意する。

### モックと再現性

- DBの検索・保存・制約が保証対象なら、実レコードを使う。検証したい判定や更新処理そのものをstubしない。
- 外部APIや発生させづらい障害は境界でstubし、その結果を受けたアプリの振る舞いを検証する。認証・権限をテストするときは、今回確認したい認証・権限判定をstubで迂回しない。
- 実行順、既存DBデータ、固定ID、実際の現在時刻に依存させない。時刻は必要なケースで固定し、データ分離や後始末は既存の仕組みを使う。
- 乱数に左右される成功条件や、固定秒数の `sleep` に頼る待機を避ける。system specはCapybaraの待機、競合の検証は条件の同期など、目的に合う既存の方法を使う。
- テストのために設計を変える必要があるなら、外部依存の境界や責務の分離を検討する。privateの公開化や依頼外の大きなリファクタで解決しない。

## 実行して検出力を確認する

- バグ修正では、可能なら修正前に再現Specが失敗し、修正後に成功することを確認する。
- TDDは仕様と入出力が明確なら使う。実装後に追加したSpecも、代表ケースで守る対象を一時的に壊したとき、意図した検証が失敗するかを確かめる。例として、在庫更新を一時的に省略し、在庫数変化の検証が落ちることを確認する。起動エラーや構文エラーによる失敗は、この確認に含めない。
- 一時変更は実装・Spec変更の依頼範囲で安全に行える場合に限り、自分の一時変更だけを戻してから再実行する。レビューのみの依頼ではファイルを変更しない。検出力を確認できなかった場合は、その理由を残す。

リポジトリ所定の環境で、関連 Spec と必須チェックを実行する。

見た目や実際の外部サービス連携は、RSpecの成功だけで確認済みにしない。必要な手動確認があれば未確認事項として残す。
自動化が難しいケースは、理由、未保証の振る舞い、手動で確認する操作と期待結果を示す。

## 完了時に伝えること

- 何の振る舞いを保証したか、または不足していたか。
- 実行したコマンドと結果。意図した失敗を確認したか、実行できなかった確認は何か。
- 残るユーザー・運用への影響があれば、その具体的な内容。

レビューの指摘は、対象箇所・見逃す不具合・最小の修正案を示す。書き方の好みだけで指摘を増やさず、変更と関係のない既存Specの一括書き換えは求めない。
